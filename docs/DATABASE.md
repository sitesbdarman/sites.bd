# Database

Status: **Step 4 — foundation + domains + auth OTP + cart.** Only the
tables below exist. Orders, services, invoices, tickets, DNS,
notifications, and admin tables are **not yet created** and will be
documented when they land.

Migration files: `database/0001_foundation.sql`, `database/0002_domains.sql`,
`database/0003_auth_otp.sql`, `database/0004_cart.sql`

## Tables

### `profiles`

Extends `auth.users` 1:1 (`profiles.id` is both the primary key and a FK to
`auth.users.id`, cascading on delete).

| Column | Notes |
|---|---|
| `id` | PK, FK → `auth.users.id` |
| `customer_id` | Unique, non-sequential, auto-generated (see below). Immutable. |
| `full_name` | Editable by the user. |
| `email` | Unique, NOT NULL. Immutable once set (mirrors the Supabase Auth email). |
| `mobile_number` | Unique. Immutable once set; editable only while still `null`. |
| `address` | `jsonb`. Editable by the user. |
| `profile_status` | `pending` \| `complete`. |
| `role` | `user` \| `admin`. Immutable via direct update — role changes must go through a trusted server-side/admin path (not implemented yet). |
| `created_at`, `updated_at` | Maintained automatically. |

**Row created by:** the application, server-side, immediately after Supabase
Auth sign-up. (The registration flow itself is a later step — this table
just needs to exist and be safe to write to when that arrives.)

## Relationships

- `profiles.id` → `auth.users.id` (1:1, cascade delete).
- `domains.owner_id` → `auth.users.id` (cascade delete).
- `hosting_plans` and `addons` have no foreign keys yet — they'll be
  referenced by future `orders` / `hosting_subscriptions` tables.

## Customer ID

- Generated by `public.generate_customer_id()`, called automatically by a
  `BEFORE INSERT` trigger on `profiles` (`trg_profiles_assign_customer_id`)
  whenever a row is inserted without one.
- Format: `CUS-` followed by 10 random uppercase alphanumeric characters
  derived from `gen_random_bytes` — **not** an incrementing sequence, so it
  can't be guessed or enumerated.
- Uniqueness is enforced two ways: a `unique` constraint on the column, and
  a collision-check loop inside the generator function itself.
- Deliberately distinct from `auth.users.id` (the Supabase Auth UUID),
  matching the requirement that the customer-facing ID never expose the
  internal auth identifier.

## Row Level Security

RLS is **enabled** on all three tables.

- **`profiles`**
  - `profiles_select_own`: a user may `select` only their own row
    (`auth.uid() = id`).
  - `profiles_update_own`: a user may `update` only their own row.
  - A separate trigger, `trg_profiles_immutable_fields`, blocks changes to
    `role`, `customer_id`, `email`, and `mobile_number` (once set) even
    under this policy — so the update policy alone is not the only line of
    defense. Users can freely edit `full_name` and `address`.
  - No public `insert` policy exists yet. Profile rows are created via a
    trusted server-side path (service-role client): the OTP registration
    flow (`app/api/auth/register/complete`) and the Google OAuth callback
    (`app/auth/callback`) both insert a row immediately after the
    `auth.users` row exists.
- **`hosting_plans`** / **`addons`**: public `select` is allowed **only**
  for rows where `is_active = true`. No write policies exist yet — writes
  will be added alongside the Admin Panel.
- **`domains`**
  - `domains_select_own`: a user may `select` only rows where
    `auth.uid() = owner_id`.
  - No insert/update/delete policy exists yet — domain rows will be
    written via a trusted server-side path once registration/renewal is
    implemented.

## `email_otps` (0003_auth_otp.sql)

Backs the registration and password-reset OTP flow. RLS is **enabled with
no policies at all** — this table is only ever read/written through the
service-role client (`lib/supabase/admin.ts`) from `lib/otp/otp.ts`, never
directly from the browser or from RLS-scoped queries.

- `otp_hash` is a salted scrypt hash (`salt:hash`) — the raw 6-digit code
  is never persisted.
- `purpose` is `'registration'` or `'password_reset'`; the two are kept
  fully separate so a code issued for one can't be replayed for the other.
- Issuing a new OTP marks any previous unused row for the same
  `email + purpose` as used, so only the latest code is ever valid.
- `attempts` caps verification tries per row; `expires_at` enforces the
  5-minute TTL. See `lib/otp/otp.ts` for the exact limits.

## `cart_items` (0004_cart.sql)

One row per domain a signed-in user has added to their cart via the
domain Claim flow (`app/domains/search`).

| Column | Notes |
|---|---|
| `id` | PK (`uuid`) |
| `owner_id` | FK → `auth.users.id`, cascades on delete. |
| `domain_name` | Not unique alone — unique together with `owner_id`. |
| `price`, `currency` | Captured at add-to-cart time from the server-side mock pricing module (`lib/domains/pricing.ts`); never a client-supplied value. |
| `validity_years` | Defaults to `1`. |
| `created_at` | Maintained automatically. |

- `cart_items_select_own` / `cart_items_insert_own` / `cart_items_delete_own`:
  a user may only select, insert, and delete rows where
  `auth.uid() = owner_id`. No update policy — items are removed and
  re-added rather than edited in place.
- `unique (owner_id, domain_name)` is the DB-level duplicate-prevention
  guarantee under concurrent requests; the API also checks before insert.
- **Guest (pre-login) cart is not modeled here.** It lives client-side in
  an httpOnly cookie (`lib/cart/guest-cart.ts`) containing only a deduped
  list of domain name strings — no price, no id, nothing sensitive. On
  the first authenticated `GET /api/cart` after login, the guest cookie
  is merged into this table (re-validating availability and
  re-computing price exactly like a normal claim — see
  `lib/cart/cart-service.ts`) and then cleared.
